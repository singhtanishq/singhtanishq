## `01 /` A little about me

I’m a software engineer who likes working at the intersection of **product thinking, systems engineering, and practical experimentation**. I enjoy taking an idea from a rough problem statement to something people can use: understanding the constraints, shaping the experience, designing the underlying logic, and improving the details that make software reliable.

I’m comfortable exploring across the stack—from interfaces and APIs to data, automation, deployment, and the operational edges around them. I’m especially drawn to work where engineering is more than connecting libraries: where the solution needs sound judgment, thoughtful trade-offs, and a clear reason to exist.

<div align="center">

> **Think clearly. Build deliberately. Make the useful thing real.**

</div>

### A quick snapshot

<details open>
<summary><strong>🧭 How I approach engineering</strong></summary>

- **Start with the problem.** Understand who needs the solution and what success should look like.
- **Map the system.** Make data, dependencies, boundaries, and failure modes visible before they become surprises.
- **Prefer clarity over cleverness.** Keep interfaces understandable, code navigable, and decisions explainable.
- **Automate the repeatable.** Use scripts and pipelines to remove fragile manual steps.
- **Verify the result.** Treat tests, observability, documentation, accessibility, and security as part of the product.
- **Keep learning.** Prototype, measure, read the source, question assumptions, and improve the model.

</details>

<details>
<summary><strong>🧠 Interests that keep me curious</strong></summary>

Product engineering · AI-assisted workflows · Search and retrieval · Developer experience · Backend architecture · Data-intensive applications · Automation · Cloud infrastructure · Application security · Research and optimization · Open source

</details>

<details>
<summary><strong>🎓 Background</strong></summary>

- B.Tech. in Electronics and Communication Engineering from IIIT Manipur.
- Silver Medalist, 2025.
- Summer research experience at IIT (BHU), focused on Wireless Sensor Networks.

</details>

Rather than tying my identity to one framework or a list of repositories that inevitably changes, I think about engineering in terms of the kinds of problems I enjoy solving.

<sub>Product workflows · Full-stack architecture · Role-based access · Integrations · Operational tooling</sub>

## `05 /` A few principles I try to keep

<details open>
<summary><strong>01 — Clarity compounds</strong></summary>

Readable code and explicit architecture reduce the cost of every future change. Cleverness is useful only when it makes the system better to work with.

</details>

<details open>
<summary><strong>02 — The interface is the whole experience</strong></summary>

A feature is not finished just because the happy path works. Error states, empty states, keyboard navigation, loading behavior, mobile layouts, and useful feedback are all part of the product.

</details>

<details open>
<summary><strong>03 — Security belongs in the design</strong></summary>

Authentication is only one part of security. Authorization, input validation, data exposure, dependency choices, secrets handling, rate limits, and failure paths deserve deliberate attention.

</details>

<details>
<summary><strong>04 — Automate carefully</strong></summary>

Automation should be observable, repeatable, and safe to rerun. A script that silently corrupts data is worse than a manual process; a useful automation makes its assumptions and failures visible.

</details>

<details>
<summary><strong>05 — Measure the real outcome</strong></summary>

The objective is not more code, more tools, or more activity. It is a better outcome for the person or system the software is meant to serve.

</details>

<details>
<summary><strong>06 — Keep the feedback loop short</strong></summary>

Small changes, reproducible environments, focused tests, clear logs, and useful documentation make it easier to learn from mistakes before they grow expensive.

</details>
